# Архитектура microTelegramAPI

[English version](ARCHITECTURE.md) | **Русская версия**

В данном документе подробно описаны внутреннее устройство, архитектурные принципы и проектные решения библиотеки **microTelegramAPI**.

---

## 1. Архитектурная философия

Большинство существующих библиотек для работы с Telegram Bot API на платформе Arduino (такие как FastBot, UniversalTelegramBot и др.) создавались в расчете исключительно на контроллеры ESP8266/ESP32 со встроенным Wi-Fi и жестко завязаны на заголовочные файлы `WiFiClientSecure.h`.

При попытке использовать такие библиотеки в реальных промышленных, охранных или полевых проектах разработчики неизбежно сталкиваются со следующими проблемами:
1. **Невозможность смены транспорта**: подключение GSM-модема (SIM800L, SIM7600), проводного контроллера Ethernet (W5500, ENC28J60) или сотового LTE-модуля требует полного переписывания чужой библиотеки.
2. **Нестабильность Long Polling на сотовой связи**: долгоживущие TCP-соединения (20–30 секунд ожидания ответа от сервера) регулярно сбрасываются сотовыми операторами, приводя к зависанию встроенных сокетов модема.
3. **Высокое потребление памяти**: монструозные парсеры и сложные внутренние очереди отнимают драгоценные килобайты оперативной памяти.

**microTelegramAPI** решает эти задачи за счёт трёх ключевых принципов:
- **Полная изоляция от деталей сетевого интерфейса**: библиотека не знает и не должна знать, каким способом передаются байты (радиомодуль, сотовая вышка или витая пара).
- **Синхронный детерминизм**: предсказуемый и надежный цикл «короткий HTTP-запрос -> чтение ответа -> закрытие сокета».
- **Zero-Overhead шаблонизация**: нулевые накладные расходы на виртуальные таблицы и динамическое связывание.

## 2. Трёхуровневая модель сетевого стека

Взаимодействие устройства с Telegram API разделено на три изолированных абстрактных уровня:

```
┌─────────────────────────────────────────────────────────────────┐
│                    УРОВЕНЬ 3: ПРИКЛАДНОЙ                        │
│                   TelegramAPI<SSLTransport>                     │
│  - Формирование JSON (sendMessage, editMessage, getUpdates)     │
│  - Парсинг входящих сообщений (ArduinoJson v7)                  │
│  - Клавиатурное меню ([MENU]), авто-HTML                        │
│  - Фильтрация доступа (strict, whiteList, threadId)             │
└────────────────────────────────▲────────────────────────────────┘
                                 │
                                 │ SSLTransport (Stream / Client API)
                                 │
┌────────────────────────────────▼────────────────────────────────┐
│                    УРОВЕНЬ 2: БЕЗОПАСНОСТЬ (TLS/SSL)            │
│  Обеспечивает шифрование трафика через порт 443 (HTTPS)         │
│  - Вариант A (ESP): WiFiClientSecure / BearSSL                  │
│  - Вариант B (GSM/Ethernet): SSLClient (программный TLS)        │
└────────────────────────────────▲────────────────────────────────┘
                                 │
                                 │ Client API (TCP socket)
                                 │
┌────────────────────────────────▼────────────────────────────────┐
│                    УРОВЕНЬ 1: ФИЗИЧЕСКИЙ ТРАНСПОРТ              │
│  Управление физическим носителем и сокетами                     │
│  - WiFiClient (ESP8266 / ESP32)                                 │
│  - TinyGsmClient (SIM800L, SIM7000, SIM7600, A9G)               │
│  - EthernetClient (W5100, W5500, ENC28J60)                      │
└─────────────────────────────────────────────────────────────────┘
```

### Преимущества такой связки
- **Модульность**: для перехода с Wi-Fi на GSM или Ethernet достаточно изменить только инициализацию объекта нижнего уровня. Основной код бота и логика `callback` остаются неизменными на 100%.
- **Переносимость**: библиотека компилируется на любых архитектурах (ESP32, ESP8266, STM32, RP2040, SAMD), где доступен базовый класс `Client` и поддержка C++ шаблонов.

## 3. Шаблонизация против полиморфизма

В классическом ООП для абстракции транспорта обычно используют интерфейсы с виртуальными методами:

```cpp
// Традиционный подход (не используется в microTelegramAPI):
class TelegramAPI {
    Client* client; // Виртуальные вызовы -> накладные расходы vtable
};
```

В микроконтроллерных системах виртуальные вызовы имеют ощутимую цену:
1. Каждая функция обращается через таблицу виртуальных методов (`vtable`), что исключает возможность инлайнинга компилятором.
2. Размер класса увеличивается за счет указателя `vptr`.
3. Требуется наследование сторонних классов от общего базового класса.

В **microTelegramAPI** применен параметрический полиморфизм через **C++ шаблоны**:

```cpp
template <typename SSLTransport>
class TelegramAPI {
public:
    TelegramAPI(SSLTransport& sslClient) : client(sslClient), apiHost(API_HOST) {}
    ...
private:
    SSLTransport& client;
};
```

### Что это даёт:
- **Прямой инлайнинг**: вызовы методов `client.connect()`, `client.print()`, `client.read()` подставляются компилятором напрямую без косвенной адресации.
- **Статический контроль типов**: любые несоответствия интерфейса клиента обнаруживаются на этапе компиляции, а не во время исполнения.
- **Универсальная обёртка TelegramESP**: для популярных плат ESP32 и ESP8266 класс `TelegramESP` просто наследует `TelegramAPI<WiFiClientSecure>` или `TelegramAPI<BearSSL::WiFiClientSecure>`, предоставляя пользователю нулевой порог входа.

## 4. Синхронный цикл и адаптивное интерактивное окно

### Защита от переполнения millis()
Для отсчёта интервалов опроса используется знаковая арифметика:

```cpp
bool isReady() {
    if ((int32_t)(millis() - nextUpdate) > 0) {
        resetTimer();
        return true;
    }
    return false;
}
```

Благодаря приведению к `int32_t`, таймер работает корректно даже в момент аппаратного переполнения счетчика `millis()` (происходит каждые 49.7 суток непрерывной работы).

### Адаптивное интерактивное окно (Adaptive Dynamic Polling)

В отличие от Long Polling, где постоянный коннект держится десятками секунд, синхронный опрос короткими POST-запросами решает проблему таймаутов GSM. Но если опрашивать сервер часто — тратится сотовый трафик, если редко — бот становится неотзывчивым.

Механизм **интерактивного окна** объединяет преимущества обоих подходов:

```
            Диалог пользователя
       ──────────────────────────────
       Входящее/исходящее сообщение
                   │
                   ▼
Базовый опрос    ┌──────────────────────────────┐    Базовый опрос
(раз в 60 сек)   │ Ускоренный опрос (1-2 сек)   │    (раз в 60 сек)
───────────────► │ Окно активности: 60 секунд   │ ─────────────────►
(Покой / Экономия) └──────────────────────────────┘ (Покой / Экономия)
```

1. **В покое**: `nextUpdate = millis() + updatePeriod` (например, 60 секунд). Сокет закрыт, трафик нулевой, модем не греется.
2. **Триггер активности**:
   - При получении любого входящего сообщения от авторизованного пользователя (`checkMessage`);
   - При успешной отправке ботом сообщения или меню (`sendMessage`);
   - При ручном вызове `bot.triggerInteractive()`.
3. **Ускорение**: окно активности сдвигает границу `interactiveWindowEnd = millis() + windowDuration`. Следующий опрос ускоряется до `interactivePeriod` (например, 2 секунды).
4. **Возврат**: как только диалог прекращается и время окна истекает, функция `resetTimer()` автоматически переключается обратно на длинный базовый интервал.

## 5. Управление памятью

Библиотека разработана с учётом жестких ограничений RAM микроконтроллеров:

1. **Строковые литералы во Flash (`F()` и `PSTR()`)**:
   Все служебные строки JSON-запросов (`F("chat_id")`, `F("parse_mode")`, `F("message_thread_id")`) и сообщения логов отладки хранятся исключительно в программной флеш-памяти и не занимают драгоценную оперативную память.

2. **ArduinoJson v7**:
   Используется современный стек `JsonDocument`, который автоматически управляет локальным буфером на стеке, предотвращая фрагментацию кучи при многократных запросах.

3. **Парсинг без копирования памяти**:
   - Метод `indexOf(',', pos)` производит поиск по символу, не создавая временных объектов `String(",")`.
   - Автодетект HTML проверяет наличие подстроки `strstr_P(message, PSTR("</"))` прямо в переданном буфере без выделения дополнительной памяти.
   - Метод `isWhitelisted` парсит 64-битные идентификаторы функцией `atoll()` по позициям разделителей без промежуточных списков.

## 6. Сравнение: microTelegramAPI vs asyncTelegramAPI

| Критерий | `microTelegramAPI` | `asyncTelegramAPI` |
|---|---|---|
| **Модель ввода/вывода** | Синхронная, блокирующая на время запроса | Асинхронная, неблокирующий конечный автомат (FSM) |
| **Поддерживаемый транспорт** | **Любой** (GSM/GPRS SIM800L, LTE, Ethernet, Wi-Fi, SSLClient) | **Только Wi-Fi** (ESP32 `WiFiClientSecure` / ESP8266 BearSSL) |
| **Удержание соединения** | Короткие HTTP POST запросы с `Connection: close` | Persistent HTTP Keep-Alive (до 30 сек без переподключения) |
| **Фоновые очереди** | Нет (вызовы выполняются непосредственно в коде) | Да (потокобезопасная очередь задач FreeRTOS на ESP32) |
| **Потребление RAM** | **Минимальное (~1–2 КБ)** | Умеренное (~8–16 КБ для очередей и стека задачи) |
| **Интерактивное окно** | Динамическое уменьшение интервала опроса | Адаптивный переключатель Long Polling ↔ Short Poll |
| **Основное назначение** | GSM-модемы, контроллеры с малым объемом памяти, полевые датчики | Нагруженные интерактивные домашние боты на ESP32 с быстрым Wi-Fi |

## 7. Резюме

**microTelegramAPI** предлагает эталонную чистоту архитектуры для встраиваемых систем:
- Независимость от оборудования благодаря C++ шаблонам.
- Адаптивное потребление трафика на сотовых сетях через интерактивное окно.
- Максимальная компактность и предсказуемость поведения.
